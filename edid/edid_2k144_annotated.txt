==============================================================================
edid_2k144.bin -- custom EDID for the USB HDMI capture card (IT68051 sink)
generated by review/scripts/edid_gen_2k144.py (python -I); byte layouts
verified against Linux include/drm/drm_edid.h + drivers/gpu/drm/drm_edid.c
and the VESA E-EDID 1.4 / CTA-861 tables (Wikipedia EDID article).
NOT copied from the EVB EDID table (iTE6805_EDID_Table.h) -- new content.
==============================================================================

== 1. Primary timing: 2560x1440 @ 144 Hz, CVT-RB geometry ==

VESA CVT v1.2 Reduced Blanking fixed geometry (verified against the
official DMT RB entries in Linux drm_dmt_modes[], e.g. 2560x1600@120RB:
HBlank=160, HFP=48, HSW=32, HBP=80, VFP=3, VSYNC=4, +hsync -vsync):

  HTotal = 2560 + 160            = 2720   (2720 % 4 == 0 -- IT68051 dual
                                          pixel DDR hard requirement)
  VTotal = 1440 + 3 + 4 + 34     = 1481   (VBlank = 41 lines)
  Pixel clock                    = 580.000 MHz
     (exact 144.000 Hz would need 2720*1481*144 = 580.078 MHz; rounded down to
      the CVT 0.25 MHz grid -> 580.00 MHz -> real refresh 143.981 Hz)
  hsync frequency = 580.0e6/2720 = 213.235 kHz
  refresh         = 580e6/2720/1481 = 143.981 Hz  ("144 Hz")
  TMDS character rate = 580 Mcsc <= 594 (HDMI 2.0 class, scrambling on)
  IT68051 dual-pixel DDR TTL PCLK = 580/4 = 145.0 MHz <= 150 MHz

NOTE (documented deviation): strict CVT-RB keeps VBI >= 460 us, which for
144 Hz would give VTotal=1621 -> 635 MHz > 594 MHz (exceeds HDMI 2.0).
The VBI is therefore shortened to 41 lines -- the universal practice for
HDMI 2.0 144 Hz sinks. All other CVT-RB geometry unchanged.

== 2. Why HF-VSDB is required ==

Sources only exceed 340 Mcsc when the EDID carries an HDMI Forum VSDB
with SCDC_Present=1 and Max_TMDS_Character_Rate>340 MHz (kernel
drm_parse_hdmi_forum_scds(): 'All HDMI 2.0 monitors must support
scrambling at rates > 340 MHz... three factors confirm: HF-VSDB present,
non-zero Max_TMDS_Char_Rate, SCDC support'). Without it the EVB EDID's
300 MHz class signalling caps the source near 297 MHz -> no 2K144.
HF-VSDB is placed immediately after the HDMI VSDB (HDMI 2.0 ordering,
enforced by edid-decode).

== 5. IT68051 register follow-up values (derived from this EDID) ==

after writing the 256 B into EDID SRAM (slave 0xA8, access enabled by
bank0 reg 0x4B = 0xA9), program -- mirrors iTE6805_EDID.c flow:
  bank0 0xC9 = 0xE5   block 0 checksum                 (EDID.c:83-84)
  bank4 0xC9 = 0xE5   (same for port 1)               (EDID.c:85-86)
  bank0 0xC6 = 0x89   VSDB physical-address offset    (EDID.c:115-116)
  bank0 0xC7 = 0x10     port0 phy addr A|B              (EDID.c:117)
  bank0 0xC8 = 0x00     port0 phy addr C|D              (EDID.c:118)
  bank0 0xCA = 0xBC   port0 block 1 checksum          (EDID.c:119)
  bank4 0xC7 = 0x20     port1 phy addr A|B              (EDID.c:121)
  bank4 0xC8 = 0x00     port1 phy addr C|D              (EDID.c:122)
  bank4 0xCA = 0xAC   port1 block 1 checksum = CKS1 + 0x10 + 0x00
                        - 0x20 - 0x00 per EVB DRV.c:111-112
  bank0 0xC5 bit0 = 0   enable internal EDID (port0)    (EDID.c:36)
  bank4 0xC5 bit0 = 0   enable internal EDID (port1)    (EDID.c:37-38)
  0xC5 bit4 reset pulse 1ms/0 per port                  (EDID.c:41-50)
  HPD stays released during all of this; our FPGA drives the HDMI HPD
  pad itself (pad LOW via init_ctrl M_ONLINE) only after stable video --
  EDID is guaranteed present before HPD, same as EVB (EDID.c:74-79 HPD
  low during write; HPD raised later by SYS state machine SYS.c:3034/3148).
